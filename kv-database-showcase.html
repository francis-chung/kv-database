KV-Database

A Lightweight Key-Value Store with Sorted Set Functionality

What is KV-Database?

KV-Database is a high-performance, Rust-based key-value database that combines the simplicity of traditional key-value stores with the power of sorted sets. Built for developers who need fast, reliable data storage with advanced querying capabilities.

Rust Tokio Async Runtime Skip Lists LRU Caching WAL Persistence Periodic Snapshots

⚡ Blazing Fast Performance

Built with Rust and powered by Tokio's asynchronous runtime, KV-Database delivers exceptional throughput with minimal latency. Features like LRU caching and skip lists ensure O(log n) lookup times for sorted sets.

🔑 Full Key-Value Functionality

Complete CRUD operations for string key-value pairs including GET, SET, DEL, EXISTS, DBSIZE, and CLEAR commands with atomic operations and WAL persistence.

📊 Sorted Set Operations

Advanced sorted set capabilities with ZADD, ZSCORE, ZREM, and ZRANGE commands. Perfect for leaderboards, priority queues, and time-series data with score-based ordering.

💾 Data Durability

Write-Ahead Logging (WAL) ensures data persistence across restarts, while periodic snapshots provide fast recovery and backup capabilities.

Available Commands

GET key

Retrieve the value associated with a key. Returns NIL if key doesn't exist.

SET key value

Set the value of a key. Overwrites existing value if key already exists.

DEL key

Delete a key and its associated value from the database.

EXISTS key

Check if a key exists in the database. Returns 1 if exists, 0 otherwise.

DBSIZE

Get the number of keys currently stored in the database.

CLEAR

Remove all keys and values from the database.

ZADD key member score

Add a member with a score to a sorted set. Updates score if member already exists.

ZSCORE key member

Get the score associated with a member in a sorted set. Returns NIL if member doesn't exist.

ZREM key member

Remove a member from a sorted set. Returns 1 if removed, 0 if member didn't exist.

ZRANGE key start stop [WITHSCORES]

Get a range of members from a sorted set by index. Optionally include scores.

How to Run KV-Database

# Clone the repository
git clone https://github.com/francis-chung/kv-database.git

# Build the project
cd kv-database
cargo build --release

# Run the server
cargo run --release

# Connect using netcat or telnet
nc localhost 7878
# Or use any TCP client

# Example commands:
SET name "John Doe"
GET name
ZADD leaderboard "Alice" 1500
ZADD leaderboard "Bob" 1200
ZRANGE leaderboard 0 -1 WITHSCORES

How It Works: Architecture

KV-Database is a small but complete storage engine. Every write is made durable before it is acknowledged, hot keys are cached, and sorted sets are backed by a hand-written skip list. All access is serialized through a single async engine behind a Mutex.

Write-Ahead Log

Every mutating command is appended to a checksummed WAL before the in-memory store is updated, so a crash can never lose an acknowledged write. Each record carries a CRC32 so torn or corrupted entries are detected and skipped on replay.

Periodic Snapshots

A background task snapshots the full dataset to a temp file and atomically renames it, then truncates the WAL. On restart the engine loads the snapshot and replays only the remaining log — fast recovery with a bounded log size.

Skip List (Sorted Sets)

Sorted sets use a custom skip list with span and rank tracking, giving O(log n) insert, remove, and index-based ZRANGE. Ordering is by score, with ties broken by member key.

LRU Cache

The key-value map is wrapped in an LRU cache (capacity 50) with hit/miss statistics, so repeated reads of hot keys skip the main hash map lookup.

Durability first: log before you apply

The SET handler writes the WAL record before mutating the store (src/server.rs):

Command::Set { key, value } => {
    let mut eng = engine.lock().await;
    let bytes = encode_record(&Command::Set { key: key.clone(), value: value.clone() });
    eng.logger.buffered_log(&bytes).await?;  // durable first
    eng.store.kv_store.insert(key, value);  // then apply
    Ok("OK\n".to_string())
}

Crash-safe snapshotting

Snapshots are written to a temp file then atomically renamed, after which the WAL is truncated (src/server.rs):

loop {
    tokio::time::sleep(Duration::from_secs(60)).await;
    write_snapshot(&cloned_engine.lock().await.store, &temp_ss_path).await?;
    std::fs::rename(&temp_ss_path, &snapshot_path)?;  // atomic swap
    truncate_wal(wal_path).await?;
}

HTTP API wrapper

The Axum HTTP layer translates JSON into the same wire commands the TCP server speaks, so both front ends share one execute_command path (src/http.rs):
