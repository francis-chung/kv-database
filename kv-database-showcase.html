A small, complete storage engine.

Every write is durable before it is acknowledged. Hot keys are cached. Sorted sets ride a custom skip list. All access serializes through one async engine.

Write-ahead logging with crash recovery

Every mutating command is appended to a checksummed WAL before the in-memory store changes, so an acknowledged write survives a crash. Each record carries a CRC32, so torn or corrupted entries are detected and skipped on replay.

Atomic snapshots

A background task dumps the full dataset to a temp file, renames it atomically, then truncates the WAL for fast, bounded recovery.

Custom skip list

Sorted sets use a skip list with span and rank tracking: O(log n) insert, remove, and index-based ZRANGE, ordered by score then member.

LRU cache on hot keys

The key-value map is wrapped in an LRU cache (capacity 50) with hit/miss statistics, so repeated reads skip the main hash map.

TCP line protocol

A Tokio async server on port 7878 speaks a simple Redis-like line protocol, one shared engine behind a single lock.

HTTP API wrapper

An Axum layer on port 8080 maps JSON onto the same wire commands, so TCP and HTTP share one execution path.

How it works.

Durability first: the log is written before the store is touched. Snapshots swap atomically. One execution path serves both protocols.

01

Log before you apply

The SET handler encodes and buffers a WAL record, then mutates the store. An acknowledged write is already durable.

02

Snapshot, then truncate

Every 60s a background task writes a temp snapshot, renames it atomically, and truncates the WAL so replay stays fast.
